СТРАТЕГІЯ «OPEN-CORE (APACHE 2.0) + ІНЖИНІРИНГ КОНФІГУРАЦІЙ (YAML)» ДЛЯ ТІР-1 РИТЕЙЛ-ХОЛДИНГІВ
01. Бар'єр входу та логіка інтер.налізації PSP (Deal Enabler) [REF: RISK-BARRIER-01]

Контекст клієнта (Холдинги рівня Fozzy Group / АТБ): Інтерналізація зовнішнього PSP (переведення фінансових потоків, маршрутизації транзакцій та токенізації всередину власного периметра) є задачею найвищого рівня критичності. Служба інформаційної безпеки (InfoSec), комплаєнс та аудит холдингу ніколи не допустять пропрієтарний «чорний ящик» від невідомого вендора в контур руху грошей.

Сценарій А: Продаж ліцензії (Блокер угоди)
Тупик «Невідомого вендора»

Спроба продати ліцензію на закритий або кастомно ліцензований код запускає захисні протоколи корпорації: 6–9 місяців аудиту прав ІВ, вимоги ескроу вихідного коду, страх зупинки бізнесу (Vendor Lock-in) у піковий сезон. Бюджет ліцензії для стартапу ріжеться закупівлею до мінімуму або угода блокується СБ.

Сценарій Б: Apache 2.0 + Впровадження (Каталізатор)
Повна прозорість та продаж інженерної експертизи

Передача ядра під стандартною ліцензією Apache 2.0 миттєво знімає вето ІБ. Холдинг отримує чистий, відкритий для SAST/DAST-аудиту код у власний репозиторій. Предметом угоди стає архітектурний консалтинг, схеми розгортання, кастомні YAML-правила процесингу та супровід.

02. Архітектурне розділення активу: Механізм vs Бізнес-логіка [REF: ARCH-SPLIT-02]

Цінність платіжного оркестратора полягає не в базовому коді маршрутизатора, а в декларативних правилах роботи з українськими банками-еквайрами (ПриватБанк, Моно, Райффайзен, ПУМБ). Система фізично і юридично розділяється на три контури:

КОНТУР 1: APACHE 2.0 (AS-IS)
Ядро виконання (Runtime Engine)

• Рушій оркестрації та абстракції API
• Усереднені синтетичні конфіги (demo.yaml)
• Відсутність ліцензійних роялті
• Чистота прав для форку та розвитку силами ІТ клієнта

➔
КОНТУР 2: РЕЗУЛЬТАТ РОБІТ (OPEX)
Бойові специфікації (YAML) та Схеми

• Каскади маршрутизації та фолбеки банків
• Мапінг кодів помилок, тайм-аути, ліміти
• Топологія розгортання під PCI DSS
• Передається за Актом впровадження

➔
КОНТУР 3: SLA / RETAINER
Зовнішній аудит та Супровід

• Навантажувальне та SecOps тестування
• Оновлення YAML-правил при зміні API банків
• Розбір складних інцидентів (split/refunds)
• Регулярний сервісний контракт

03. Порівняльна матриця: Зняття ризиків та економіка угоди [REF: ECON-MATRIX-03]
Параметр оцінки Класичний продаж ліцензії (CAPEX / IP) Модель Apache 2.0 + Впровадження та YAML (OPEX)
Бюджетування та Закупівлі Складний CAPEX-комітет. Тривала оцінка нематеріального активу, жорсткий пресинг за ціною для невеликого вендора. Швидкий OPEX (ІТ-послуги / Консалтинг). Проходить через стандартні бюджети на розбудову інфраструктури та зовнішню експертизу.
Юридичні ризики наших зобов'язань Вимоги гарантій чистоти патентів, фінансова відповідальність вендора за збої в коді на мільйонних оборотах ритейлу. Зняття ризиків з нас: Ядро надається за Apache 2.0 (відмова від гарантій на код). Ми відповідаємо виключно за узгоджений обсяг робіт з налаштування та тести на фіксованому коміті.
Ризики для Холдингу (Клієнта) Ризик залежності від одного постачальника, закритий код у фінансовому ядрі, неможливість самостійної модифікації. Повна автономність: Міжнародна ліцензія Apache 2.0 гарантує право безперешкодно розвивати систему власним R&D-департаментом (напр., TemaBit).
Фінансовий потенціал чека Низький стартовий поріг: корпорація не заплатить значну суму за «коробку» компанії без гучного імені. Вищий сукупний чек (LTV): Вартість проєктування архітектури, бойових YAML-профілів, SecOps-тестування та SLA перевищує потенційну ціну «голої» ліцензії.
04. Резюме для прийняття рішення [REF: EXEC-SUMMARY-04]
01 // ВХІД У ПЕРИМЕТР

Ми не намагаємося продати холдингу «кота в мішку» для управління його грошима. Ми даємо прозорий інженерний фундамент і продаємо інтеграцію та знання предметної області.

02 // ЮРИДИЧНИЙ ЩИТ

Відсутність договору про передачу виключних прав ІВ економить місяці погоджень. Ми не несемо токсичної відповідальності за код ядра, здаючи конкретні етапи робіт (UAT).

03 // МОНЕТИЗАЦІЯ ЗНАНЬ

Усереднений YAML у коді робить систему безпечною для відкриття, але без нашого впровадження, схем розгортання та тонкого налаштування процесингу вона не дає бізнес-ефекту.
